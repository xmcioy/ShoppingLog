# 购物记录技能（shopping-log-recorder）

## 固定路径（不可更改）

- 项目根目录：`<KNOWLEDGE_ROOT>`
- 记录目录：`<KNOWLEDGE_ROOT>/entries/`
- 图片目录：`<KNOWLEDGE_ROOT>/entries/images/`
- 索引文件：`<KNOWLEDGE_ROOT>/index.md`
- 网站项目根目录：`<PROJECT_ROOT>`
- 网站数据库：`<PROJECT_ROOT>/data/shopping.db`
  - 低耦合分表：公共字段（名称/价格/日期/渠道/评分/标签/评价/图片/单价/原始价/实付价/抵扣/复购/purchase_history/product_group/flavor_name 等）存 `items` 主表；品类特有字段按品类路由到扩展表（`item_id` 关联主表 1:1）：食品/餐饮 → `food_items`（保质期/生产日期/到期日/配料/营养/厂商/许可证/口味 flavors 等），药品保健 → `health_items`（适应症/用法用量/禁忌/不良反应/注意事项/批准文号等），美妆护肤 → `beauty_items`（保质期/配料/厂商/产地等），衣服/鞋/包配/运动户外/母婴 → `clothing_items`（尺码/颜色/材质/洗涤/款式/季节等），数码家电 → `electronics_items`（型号/配置/保修/序列号等）；同表只放属性相同的品类，属性不同分表
- 网站数据文件：`<PROJECT_ROOT>/site/data.js`
- 网站图片目录：`<PROJECT_ROOT>/images/`（`site/images` 软链指向此处）

每次写入必须使用上述绝对路径，禁止因会话/工作目录变化而改写到别处。

## 记录流程（按顺序执行）

1. **解析信息**：从用户消息与附件中提取字段；**食品类必须先做「图片信息全量提取规则」的逐张图片解析**（含生产日期/到期日、食用方法原文、口味信息四条红线），再按「商品分类特有属性清单」补分类特有字段，最后按「价格记录与换算规则」处理价格。通用字段：日期（默认当天）、品类（食品/衣物/鞋/其他）、商品名、品牌、单价/总价、原始价格/实付价格（若有）、数量、购买渠道、评分（满分5，支持半星如2.5）、标签、评价原文；数量与总克数/单个克数信息一并标记（单个克数未提供可按 总克数÷数量 换算并注明"换算"）
2. **确定编号**：`YYYYMMDD-序号`，序号为当天已有记录数 +1（不足两位补零）；图片与记录文件共用该编号前缀
3. **保存图片（多图保存）**：附件图片**除下列三类外全部保存**到 `entries/images/<编号>-<序号>.<ext>`（多张按序号命名，主图/商品外观图排第 1 张）：**① 配料表特写图**（仅拍配料表区域的照片，不存，文字已录入）；**② 详情介绍图**（商品详情页介绍/大段产品介绍文字图，不存）；**③ 订单页截图**（含收货人/电话/地址等隐私信息，不存，仅提取文字）。其余图片——包装正面/背面/侧面、实物图、营养成分表、制作方法/食用方法、材质水洗标、说明书等——**全部保存**。需保存的图片必须压缩：`sips` 压缩到最长边 ≤1280px、JPEG 质量 ≤80、单张 ≤300KB；HEIC 等先转 JPEG/PNG。若用户明确要求保留某张资料图再额外保存。网站同步时 `--image` 可重复传入全部图片
4. **写入记录**：按「记录模板」写 `entries/YYYY-MM-DD-<编号>-<商品名>.md`，模板中所有图片可读字段必须填齐，不得留空可读项
5. **更新索引**：追加到 `index.md` 条目清单，刷新统计概览（总条目数/总花费/品类分布）
6. **同步网站（必须执行，且必须验证）**：调用 `<PROJECT_ROOT>/scripts/shop.py add` 将同一条记录写入网站数据库（参数映射见「商品分类特有属性清单」表格：通用 `--name/--price/--category/--subcategory/--brand/--date/--quantity/--channel/--place/--rating/--review/--tags/--repurchase/--image/--source/--ingredients/--flavors/--nutrition/--nutrition-note/--original-price/--paid-price/--gift-card-value/--jd-bean-value/--product-group/--flavor-name`；食品包装 `--standard-no/--entrusting-party/--entrusting-address/--manufacturer/--manufacturer-address/--manufacturer-phone/--origin/--storage-condition/--shelf-life/--produced-date/--expiry-date/--service-hotline/--license/--allergens/--tips/--eating-method/--image-desc`；分类特有 `--specs/--indications/--dosage/--contraindications/--adverse-reactions/--cautions/--approval-no/--purchase-history`；`--image` 可重复传入，图片自动复制到 `<PROJECT_ROOT>/images/YYYY-MM/`），随后运行 `sync_site.py` 重新生成 `site/data.js` 并自动为 `index.html` 中 data.js 引用打版本号。**同步后必须四步验证**：① `site/data.js` 中存在新记录（grep 商品名）；② 本地 `curl http://127.0.0.1:8088/data.js` 返回新记录；③ 远程 `<REMOTE_URL>/data.js?v=<版本号>` 返回新记录（<REMOTE_URL> 为部署站点的公网地址）；④ nginx 配置 `<NGINX_CONF>`（示例见 <PROJECT_ROOT>/docs/nginx.shopping.conf.example） 对 .js 已设 `no-cache`，改过配置后执行 `nginx -t && nginx -s reload`。任何一步不通过需修复后继续，不能以"已写入 db"视为完成
7. **同步腾讯文档（必须执行）**：按「同步到腾讯文档」章节将本条记录覆盖式同步到固定文档（删除该商品旧记录块，写入最新记录，不追加）
8. **确认结果**：回复中给出记录摘要、文件路径；食品类给出分析建议摘要；速食/衣物/说明书类给出解读摘要

> 参数注意事项：`shop.py add` 的 `--category` 默认"其他"，食品请传"食品"；`--nutrition` 格式为 `能量=1484,蛋白质=9.0,脂肪=0.6,碳水=77.0,钠=164,钙=125`（每100g，可省略单位）；`--tags` 逗号分隔；`--repurchase` 取 yes/no/maybe；`--rating` 1~5 支持 0.5 步进。价格类：`--price` 填**实际商品价格**（京东场景 = 实付价格 + 礼品卡价值 + 京豆价值；盒马/饿了么等生鲜外卖场景 = 实际到手价/实付单价；软件中心/应用商店积分兑换场景 = **1积分=1元**，积分值即金额，如 18.20积分 = 18.20元；**若该积分价是多件/多包总价（订单写“8包”“6瓶”等），price 必须记单件单价 = 总价÷件数（如 18.2元÷8包=2.275元/包），quantity 记件数（8），严禁把总价当作单价**）；**所有场景必须记录单价**（单份/单袋/单个价格，页面显示的常为多份/整组总价，须除以份数换算单价后记录，quantity 记份数）；`--original-price` 原始价格/标价（京东 = 订单商品总额；盒马/饿了么 = 订单详情划线价，必须填划线价）；`--paid-price` 实付价格；`--gift-card-value`/`--jd-bean-value` 礼品卡/京豆抵扣（有则填）。若某次只有 Markdown 记录、未同步网站（历史遗留），补跑第 6 步修复。

## 图片信息全量提取规则（食品类必读，唯一权威清单）

1. **总则**：用户提供商品包装/标签/营养成分表等图片时，必须逐张用 OCR/视觉解析读取，**图片上所有可读信息全量字段化**，禁止只提取名称/价格/评价而遗漏日期、厂商资质、许可证、食用方法等字段。
2. **必提取字段清单**（逐张核对，图片可读则必须全部提取，缺项不编造）：
   - 产品名称（含规格版本）、产品类型/属性（如"速冻米面制品（熟制品 非即食）"）、净含量
   - 产品标准号（如 GB 19295）、食品生产许可证编号（SC 编号）
   - **生产日期（produced_date）与到期日/保质期至（expiry_date）：两者是独立字段，图片上有就必须各自记录，禁止只记其一或合写一行**。常见形态：背面印"生产日期：2026/07/22"、另印"保质期至：2027/07/21"，或正面印"生产日期及保质期至见包装背面"（此时如实记录该指引原文，并翻查背面/喷码）；到期日可由 生产日期+保质期 推算时注明"推算"
   - **喷码必须复核（红线强化）**：凡包装出现"见背面喷码/见包装背面/生产日期见XX"类指引，**必须翻到对应面并放大复核（PIL resize 2.5x + 增强对比后重 OCR）读取真实日期喷码**，生产日期与到期日/保质期至都要落地；严禁把"见包装背面"指引当最终答案
   - **到期日推算必须执行**：拿到生产日期后必须结合保质期计算到期日（如 2026-01-05 + 12个月 → 到期 2027-01-04，注明"推算"）；记录完成时若发现临近/已过期风险，在评价或备注中提示
   - 保质期（如 12个月）、贮存条件（如 -18℃及以下冷冻保存）、产地
   - 生产商/制造商（名称+地址+电话）、委托方/品牌方（名称+地址）、全国服务热线
   - 配料表、营养成分（每100g：能量/蛋白/脂肪/碳水/糖/钠等）、致敏物质/过敏原提示、温馨提示
   - **口味/风味（flavors）：多口味、多拼、多组合食品（如八拼蛋糕、什锦装零食、混合口味礼盒等）图片标注的每种口味名称必须逐一提取，含每种口味的数量/块数/占比；单一口味商品图片未标注口味时留空，禁止凭配料臆造**。常见形态：包装正面写"4种口味 低糖配方"、背面写"经典提拉米苏/开心果巴斯克/草莓酸奶芝士/榛果芝士 各2块"，必须把每种口味名称和数量都记录全
   - **食用/烹饪方法（eating_method/cooking_method）：必须逐字转录包装原文**——保留原句、标点、步骤顺序、时长、火候、水量、工具等全部细节，禁止总结、缩写、合并句子、转述
3. **模糊与缺失处理**：
   - 图片未显示具体日期（如写"见包装正面喷码"）→ 如实记录该指引原文，**禁止编造具体日期**
   - 图片文字模糊 → 如实说明并请用户补发清晰图，不猜测
   - 图片确实没有该字段 → 留空，不编造
4. **完成度自检**：写入数据库前按第 2 条清单逐项核对，**生产日期、到期日、食用方法原文、口味信息为四条红线**，任一字段图片可读但未提取即为缺陷，须回图重读。

## 商品分类特有属性清单（每类商品必提取属性，落库参数唯一权威映射）

按商品类别提取该类特有的属性，**图片/说明书可读时逐项提取，缺项不编造**。通用字段（名称、品牌、价格、日期、数量、渠道、评分、标签、评价）所有类别都要记录。

## 营养成分表与配料表处理规则

1. **识别**：用户提供营养成分表/配料表（照片或文字）时，用 OCR/视觉解析提取数值；文字版直接结构化
2. **统一单位**：优先按"每100g"或"每份"标注，转换时注明换算基准
3. **关键指标**：能量、蛋白质、脂肪、碳水化合物、糖、钠为必记；有其他指标（膳食纤维、钙、反式脂肪等）按需记录
4. **配料表分析**：排序靠前的配料含量高（按国标按添加量递减排序）；标注高糖/高盐/高油风险、常见添加剂、过敏原
5. **分析建议**（每次给出，简明扼要）：一句话健康定位；适合/不适合场景或人群；与同类常见商品的粗略对比（基于已有知识，不虚构具体竞品数据）
6. **免责**：分析基于公开营养常识，不构成医疗建议；用户有特殊健康状况以医生意见为准

## 速食类制作/烹饪方法处理规则

1. **识别**：速食/方便食品（方便面、自热食品、预制菜、冲调粉、速冻面点等）图片含制作/烹饪说明（包装背面/附卡）时，用 OCR/视觉解析提取
2. **原文转录（强制，红线）**：将图片中的说明**逐字转录为文字**，保留原句顺序、标点、步骤、时长、火力/微波档位、水温/水量、工具、是否需要解冻/开火/自热等全部细节；**禁止总结、改写、缩写、合并句子、转述**。例如包装写"把蒸锅水烧开（包子无需解冻），蒸架垫上蒸笼布或蒸笼纸菜叶代替，放入包子，大火8-10分钟即可食用"就必须原样记录，不得写成"蒸8-10分钟"
3. **可选要点**：原文转录之后可另起一行附一句操作核心便于日后回忆，但**要点不得替代原文**，且必须标注"要点"
4. **无法识别时**：如实说明，不臆造烹饪参数

## 衣物/纺织品材质与洗涤方法处理规则

1. **识别**：衣物/纺织品（衣服、鞋、床品、毛巾等）图片含材质标签（水洗标）时，用 OCR/视觉解析提取
2. **材质记录**：纤维成分及占比（如棉70%/涤纶30%）、产地、货号
3. **洗涤方法记录**：水洗标符号与文字转译为文字——最高水温、机洗/手洗/干洗、漂白限制、熨烫温度档位、烘干方式、晾晒注意、特殊提示（如不可浸泡）
4. **保养提示**：按材质常识补充简要保养建议（如羊毛需冷水+平铺晾干），不虚构具体参数
5. **无法识别时**：如实说明，可结合商品本身信息记录通用护理要点并注明"未见图标"

## 说明书处理规则

1. **识别**：附件含说明书/使用说明（商品自带说明书照片、包装上说明文字等）时，解读并记录
2. **记录要点**：商品用途、组装/安装/使用方法步骤、安全注意事项、清洁保养、保修条款/客服联系方式等关键信息
3. **文字化**：说明书为图片时用 OCR/视觉解析转为文字摘要；保留关键数字（规格、参数、时限）不臆造
4. **篇幅控制**：长说明书只记要点摘要，不逐页照抄

## 图片压缩规则

1. **多图保存**：附件图片除「配料表特写图 / 详情介绍图 / 订单页截图」三类外**全部保存**（与「执行步骤-保存图片」一致）；每张按 `<编号>-<序号>.<ext>` 命名，主图/商品外观图排第 1 张
2. **保存的图片必须压缩**：最长边 ≤1280px，JPEG 质量 ≤80，单张目标 ≤300KB
3. **实现方式**：macOS 用 `sips -Z 1280 -s format jpeg -s formatOptions 80 <in> --out <out>` 等命令压缩；HEIC/PNG 等先转 JPEG 再压缩
4. **命名与替换**：压缩后保留原编号-序号命名；网站同步用的图片同样用压缩后的版本
5. **例外**：若保存的图片含需辨认的小字（如包装说明），压缩后难以辨认时，可适当放宽至最长边 1600px，但质量仍 ≤80

## 价格记录与换算规则

1. **字段定义**：`original_price` 原始价格/标价；**京东/一号店等平台 = 订单「商品总额」；盒马/饿了么等生鲜外卖平台 = 订单详情/交易完成页中划线（划掉）的价格**（画删除线那个价，如「¥10.45 划线价 ¥19.9」→ original_price=19.90）；`paid_price` 实付价格（最终支付金额）；`gift_card_value`/`jd_bean_value` 礼品卡、京豆抵扣价值（京东/一号店等平台，有则记录）
2. **京东场景换算**：**实际商品价格 = 实付价格 + 礼品卡价值 + 京豆价值**；统计与 `--price` 一律用实际商品价格。**商品优惠/优惠券/红包是平台让利，不计入实际商品价格**——严禁只看"实付金额=0"就判为0元，必须逐项核对抵扣明细
3. **完整示例**：京东订单商品总额 29.90 元，京豆抵扣 2.14 元、商品优惠 10.34 元、礼品卡抵扣 17.42 元、实付 0 元 → `original_price=29.90, paid_price=0, gift_card_value=17.42, jd_bean_value=2.14, price(实际)=19.56`（商品优惠 10.34 为平台让利不计入）
4. **盒马/饿了么等生鲜外卖平台换算（不套京东公式）**：`original_price` = 订单详情/交易完成页中**划线（划掉）的价格**（用户定义的原价，必须优先取划线价，不是实付价）；`price` = 实际到手价/实付单价（划线价下方那个价格）；`paid_price` = 实付金额（多件整单时按比例分摊）。若同时出现「原价」与「划线价」两个值，**以划掉的那个（划线价）为准**
5. **订单明细提取**：识别订单截图时必须逐行读取全部金额条目（商品总额/运费/京豆抵扣/商品优惠/礼品卡抵扣/实付金额，以及盒马/饿了么订单每行的 实付单价/划线价），逐项填入对应字段，不得遗漏；盒马/饿了么订单每行都必须把划线价写入 original_price
6. **无礼品卡/京豆时**：如实记录 `original_price` 与 `paid_price`，`price` 取实际支付金额，并在记录中注明优惠方式，不臆造抵扣明细
7. **买入价（每次购买必记，含首次）**：每次买入记录当次的 实际价/原始价/实付价/礼品卡/京豆抵扣/数量/来源/生产日期/到期日，**首次购买即建立该商品 `purchase_history` 第一批**，之后每批按时间先后追加到 `purchase_history`（JSON 数组），并同步用 `--purchase-history` 传给 shop.py；查询历史价格以 purchase_history 为准
8. **不同规格/版本各自记价**：同一商品的不同规格/不同版本是独立价格序列，各自维护 `purchase_history`，禁止混记
9. **价格与评分缺失必确认**：每次购买记录**必须提供价格（实际价/原价/实付/抵扣明细）与评分**；若图片/订单信息中没有价格或评分，**必须先向用户询问确认**（请用户提供价格/评分，或确认采用某值），得到答复后才落库，禁止自行省略、猜测或复用历史值

## 同商品多次购买与版本/规格管理

1. **同一商品判定**：品牌 + 商品名一致即为同一商品（例：超盒算NB 经典蛋黄酥 330g·6个 与 480g 是同一商品的两个规格版本）
2. **版本划分**：同一商品下按【规格/总克数/容量/型号】或【配料表/营养成分/配置变更】划分版本；配料无变更时同一规格视为同一版本
3. **每个规格/版本独立成档**：各自维护独立的购买批次列表（purchase_history），每批含 日期、实际价/原价/实付价、数量、来源、生产日期、到期日、保质期；**禁止把不同规格的批次混在一起**。有规格差异时商品名带规格标识（如"经典蛋黄酥 330g·6个"）
4. **首次购买某规格**：按记录模板创建完整条目（含配料/营养/配置/日期/厂商等分类特有属性），**同时为 `purchase_history` 建立第一批记录**（含当次 日期/实际价/原价/实付价/数量/来源/生产日期/到期日）；已存在条目若因历史原因缺 purchase_history，需补建第一批后再继续追加
5. **再次购买同一版本**（规格与配料均未变更）：知识库在同一商品条目下追加一条购买批次（日期 + 实际价/原价/实付价 + 数量 + 来源 + 生产日期 + 到期日），**不重复记录配料表与营养成分**；并将该批次追加进该版本的 purchase_history。网站照常 `shop.py add` 一次（name 带规格版本标识），用 `--purchase-history` 带上累计批次
6. **规格或配料变更**：视为新版本，在同一商品条目下新增"版本"小节记录新规格/新配料/新营养及变更点；该版本后续购买批次追加到对应版本小节
7. **每批三日期必记（红线）**：每次购买记录**必须找到并记录当批的生产日期、保质期、到期日**——包装/喷码/电子详情可读则记录；**拿到生产日期后必须按 生产日期+保质期 推算到期日并注明"推算"**；**找不到生产日期/保质期/到期日时，必须询问用户确认（补图/提供），禁止直接写"未知"、编造或复用上一批日期**；同一商品不同批次生产/到期日不同，逐批记录
8. **溯源记录**：生产商、产地、批次号、溯源平台等溯源信息有则记录到条目溯源字段，无则不写、不虚构
9. **价格记录**：每次购买记日期 + 实际价（含原价/实付价/抵扣明细）+ 来源（以购物订单信息为准），按时间先后排列，便于查询历史价格
10. **网页展示（purchase_history 独立折叠块）**：多次购买记录在网站 index.html 商品卡片下方独立折叠块「购买记录 · N 次」中逐行展示，每行含买入时间、数量、价格明细（实价/原价/实付/礼品卡/京豆，有则显示）、**生产日期/保质期/到期日（每次购买均展示，因每批不同）**、来源（source/channel，以购物订单信息为准）；无多次购买记录（无 purchase_history）时不渲染该块

## 同产品多口味拆分与关联（flavor variant）

**触发判定**：同一产品（同品牌、同系列）购买/记录了多个**口味 / 克数规格 / 颜色花色**变体时，**每个变体独立成条记录**，同时通过 `product_group` 关联为同一产品，网站自动聚合展示。典型例子：品牌A脆脆条 25g×8袋 的 口味B 与 口味A；同款衣服不同颜色/尺码同理。

1. **拆分记录**：每个口味独立调用一次记录流程，各自编号（YYYYMMDD-序号），知识库各自独立条目，网站各自 `shop.py add` 落库（评分/回购/评价可以不同：如 柠檬味4星不回购、茉莉口味3.5星不回购）
2. **关联字段**：
   - `product_group`：同组所有口味条目共享同一 ID（命名 `<品牌拼音>_<系列>_<YYYYMMDD>`，如 `brand_series_YYYYMMDD`）
   - `flavor_name`：本条口味名（如 `口味B`、`口味A`），作为网站聚合卡片 tab 标签；对应 `shop.py add` 参数 `--product-group`、`--flavor-name`
   - 商品名写法：`<产品名>·<口味名>（品牌 规格）`（如 `小桂气脆脆条2.0·口味B（品牌A 25g×8袋）`）
3. **评分与评价**：每条口味独立评分、独立回购判断、独立评价；同组口味可比较着写（如"口味A不如口味B，都不如品牌C"）
4. **网站展示**：同 `product_group` 的条目自动聚合成一张卡片，顶部 tab 显示各口味名，点击 tab 切换该口味的面板（价格/评分/评价/日期/图片等各自独立）。`sync_site.py` 重新生成 data.js 后自动生效
5. **腾讯文档**：每个口味独立商品块（`## <商品名>【最新】`），表格中"口味组"行写明同组关联与另一口味名；按各自商品名覆盖式更新
6. **与 flavors 字段的区别**：`flavors` 用于"单条记录内多口味拼装/多拼食品"（如八拼蛋糕，一个商品含多种口味）；`product_group + flavor_name` 用于"同一产品分口味独立成条记录"（每个口味有自己的评分/回购）。两者独立使用，不互斥
7. **品类汇总（网页默认视图）**：网站默认展示「品类汇总」视图，按 category 聚合所有记录（每类卡片显示件数、金额、占比、含变体提示），点击品类卡进入该品类卡片明细；明细卡片对同 product_group 的变体以 tab 切换（flavor_name 即 tab 标签，涵盖口味/克数规格/颜色花色）。记录时同品类不同口味/克数/颜色一律独立成条并带 product_group/flavor_name；明细始终用原表，汇总仅用于网页展示
